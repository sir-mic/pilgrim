1. Overview & system diagram

mic (internally Pilgrim, package pilgrim_app) is a free Android app for reading the Bible a little at a time. It ships reading plans (one chapter a day), a daily reflection prompt, a journal, progress tracking, and an optional quiet daily reminder.

The whole project is split across four pieces:

  • App — Flutter/Android app that stores everything locally in SQLite.
  • Content — a signed, data-driven "content bundle" (plans, prompts, notification copy) that the app can refresh without an app update.
  • Landing page — a GitHub Pages site with the download button and the feedback form.
  • Feedback API — a Cloudflare Worker + KV that stores feedback submissions privately.

3.2 Startup flow (lib/main.dart)

  1. main() initialises the notification service, then runs the app inside a Riverpod ProviderScope.
  2. The bootstrap provider seeds the bundled content (verifies the signature, reconciles into the DB) and restores the saved theme.
  3. If not onboarded → OnboardingScreen; otherwise → HomeShell.
  4. After first frame, HomeShell silently checks for a remote content update and re-schedules the daily reminder if enabled.

4. Content pipeline & signing

Reading content is data, not code. A signed JSON bundle carries plans, prompts and notification messages. The app ships a copy (offline first) and can pull a newer bundle from the web — no app update required.

4.1 The pilgrim_content package (content/, local path dependency)

FilePurpose
lib/src/models.dartContent models (SignedBundle, plans, readings…).
lib/src/validation.dartContent validation.
lib/src/canonical_json.dartCanonical JSON so signatures are stable.
lib/src/signing.dartEd25519 sign/verify helpers.
lib/src/book_table.dart, built_plans.dart, mcheyne_parser.dart, default_copy.dartPlan/verse helpers and defaults.
bin/pilgrim_build.dartCLI: keygen and build.

4.2 Build commands

cd content
dart run pilgrim_build keygen      # new Ed25519 key pair → keys/private_key.pem (+ printed public key)
dart run pilgrim_build build       # validate + sign source/mcheyne-plan.json
                                   # → build/content.json and ../app/assets/content/content.json

4.3 Verification & reconcile (in the app)

  • The app embeds the public key (signature_verifier.dart).
  • On first run it verifies the bundled asset and seeds the DB.
  • On launch it fetches https://sir-mic.github.io/pilgrim/content.json, verifies the signature, and reconciles if the version is newer. Failures are silent — the app keeps its last-known-good local copy and stays usable offline.
  • Reconcile upserts plans, replaces prompts/messages; user progress and journal are never touched.

7. Feedback API (Cloudflare Worker + KV)

Live worker: https://divine-glitter-11cefeedback.mikeharoldhandig12.workers.dev · Source: site/worker/feedback-worker.js · Deploy steps: site/worker/README.md.

7.1 Endpoints

Method + pathBehaviour
POST /Stores { name, type ("bug"|"suggestion"), message, date } in KV. Returns 201.
GET /feedback?key=…Returns { "items": […] } newest-first. 403 without the secret key.
OPTIONS204 with CORS headers (writes are open so the site can submit).

7.2 Setup summary

  • Cloudflare Worker with a KV namespace binding named FEEDBACK.
  • Text variable FEEDBACK_SECRET = your private read key.
  • Read feedback at /feedback?key=YOUR_SECRET (browser or curl).
# submit
curl -X POST https://…workers.dev -H "Content-Type: application/json" \
  -d '{"name":"Tester","type":"bug","message":"Reminder fired early"}'

# read (private)
curl "https://…workers.dev/feedback?key=YOUR_SECRET"

8. Build & release process

8.1 Building the APK

cd app
powershell -ExecutionPolicy Bypass -File .\build-apk.ps1
# → build\app\outputs\flutter-apk\mic-app.apk  (≈58 MB)

The script runs flutter build apk --release then renames the artifact to mic-app.apk (Flutter always emits app-release.apk internally).

8.2 Signing & updates (data safety)

  • Release builds are signed with the debug keystore (~/.android/debug.keystore).
  • Updating keeps all data (journal, progress, settings) as long as the new APK has the same signature and a version code ≥ installed.
  • Building on a different machine produces a different debug keystore → signature mismatch → install fails and data would be lost after a forced uninstall. Build on this machine.
  • Version lives in app/pubspec.yaml (version: name+build). Bump it on every release.

8.3 Publishing a release

  1. Build mic-app.apk (above).
  2. On sir-mic/pilgrim → Releases → create/edit release with tag matching the app version.
  3. Attach mic-app.apk (the landing page download link expects that filename).

10. FAQ & troubleshooting

Will updating the app lose my journal/notes?

No — if the new APK has the same signature and an equal-or-higher version code, Android upgrades in place and keeps all data. Data is only lost on uninstall, factory reset, or a signature mismatch (see §8.2).

The download button on the site returns nothing.

It only works once a release exists on sir-mic/pilgrim with an asset named mic-app.apk.

How do I see feedback submissions?

Visit https://divine-glitter-11cefeedback.mikeharoldhandig12.workers.dev/feedback?key=YOUR_SECRET in a browser, or download as JSON with curl.

Feedback form says the worker URL isn't set.

In site/index.html, the API_URL constant must be the live worker URL (it currently is). A YOUR_WORKER_URL_HERE placeholder means it wasn't wired up.

I changed content — how do installed apps get it?

Rebuild with pilgrim_build build (bump --version), publish content.json to the GitHub Pages manifest, and rebuild the app asset for new installs. Installed apps pull the newer manifest automatically on launch.
